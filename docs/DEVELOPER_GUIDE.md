# Developer guide

## 1. Add or disable factors

Edit `examples/refund_agent/policy.json` using documented factor names and strict config. Mandatory `authorization` must remain enabled. Other factors may be set to `{"enabled": false}`. A disabled factor has no effect on local preflight and appears as disabled in the Control Card. Advisory factors never claim to have evaluated a use case.

## 2. Check without executing

```python
record = kit.check(action_request)
print(record.verdict)  # ALLOW, BLOCK, REQUIRE_APPROVAL
print(record.as_dict())  # minimal, no raw prompt/actor ID
```

## 3. Route a demo action through a guard

```python
try:
    decision, result = kit.execute_guarded(request, simulated_executor)
except ActionNotAuthorized as error:
    send_to_user_for_review(error.record.verdict)
```

The wrapper never runs the callable when the result is not `ALLOW`. This is *not* a universal gate: callers can bypass it. Your real enterprise system must establish an authoritative server-side enforcement and audit boundary.

## 4. Add an independently implemented factor

Use the public `FactorFinding` and a `custom_factors` mapping; see `examples/custom_factor.py`. Do not feed custom factors untrusted policies generated by an LLM. A custom factor exception blocks the local action preflight. Custom plugins must be packaged by developers and are not loaded dynamically from user-submitted imports.

## 5. Human approval integration

If `human_oversight` matches and there is no `approval_verifier` callback, verdict is `REQUIRE_APPROVAL`. To supply one, build an **application-owned verifier** that independently checks an authenticated approval receipt bound to exact use case, actor, tenant, action, resource, environment, expiry, revocation and separation-of-duties policy. The kit itself does **not** create or verify cryptographic proofs.

Do **not** treat `"approved": true` in an agent's tool payload as an approval. Do **not** plug model output directly into approval verifier. `examples/refund_agent/trusted_approval_demo.py` is only a fake in-memory illustration, not an authorization example to put in production.

## 6. Control Cards

Generate a JSON or Markdown card for an auditable configuration *summary*:

```bash
PYTHONPATH=src python -m trustelis_rai card --policy examples/refund_agent/policy.json --format markdown
```

The card shows `NOT_EVALUATED` for fairness and regulation rather than certifying compliance. A `DecisionRecord` is an independent **prototype preflight record**. No persistent tamper-proof audit capability is included.

## 7. Provider adapters and extensibility

v0.1.0 uses no external API and should be usable with any agent framework via a trusted host integration. Future integrations may offer source/target adapters, OpenAI/Anthropic telemetry, CI checks, and GitHub Actions. These features are *planned*, not present in this release.
